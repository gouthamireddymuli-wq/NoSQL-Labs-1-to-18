Verification Pipeline
1 Seed Collection
Insert 500 deterministic documents into nosql_labs.backup_demo and record a SHA-256 baseline checksum.
2 mongodump Backup
Dump the collection to a timestamped directory under backups/. RTO clock starts here.
3 Simulate Data Loss
Drop the collection — zero documents remain.
4 mongorestore
Restore from the dump directory. RTO timer stops here.
5 Dual Verification
Compare document count AND content checksum. A count match alone would miss silent corruption.
Why count AND checksum?

If mongorestore silently drops or duplicates even one document, the count check alone could still pass (drop one, duplicate another → same total). The SHA-256 checksum is computed over all field values, sorted by order_id, independent of insertion order and _id regeneration.

Scenario: mongorestore succeeds but drops 1 doc and duplicates another → count passes, checksum fails → backup is unverified and cannot be trusted.

RPO & RTO — Business Context
RPO — Recovery Point Objective
How much data you can afford to lose. Determined by backup frequency. If you dump every hour, your RPO is ~60 minutes of potential data loss.
RTO — Recovery Time Objective
How long you can afford to be down. The restore timer above gives you a real RTO data point for this collection size.
