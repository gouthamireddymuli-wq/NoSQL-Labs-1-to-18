Multi-Tenant MongoDB Isolation Strategies Matrix

Architectural Trade-offs
Isolation Approach Isolation Level Key Advantages (Pros) Key Constraints (Cons)
Shared Collection
{"tenant_id": id} 		Medium Lowest operational cost, single set of indexes, frictionless tenant onboarding, minimal connection overhead. Application-level filtering mandatory in every query; high risk of BOLA/IDOR if filter is omitted. Shared resource contention.
Collection-per-Tenant
db.tenant_{id}_tasks 		Strong Simpler RBAC, collection-level drop/backup, logical isolation, separate index spaces per tenant. Namespaces and file descriptor limits at scale (thousands of collections); cross-tenant reporting becomes complex.
Database-per-Tenant
tenant_{id}.tasks 		Strongest Physical data isolation, compliance ready (GDPR/HIPAA), dedicated storage quotas, easy drop/restore per tenant. Higher memory & connection pool overhead; resource pooling across small tenants is inefficient.
Activity 1 Analysis: Cross-Tenant Vulnerability
Question: What would go wrong concretely if update_task filter only checked {"_id": task_id} without also checking tenant_id?

Concrete Vulnerability Scenario:

  1. Suppose Acme Corporation creates critical task t1 with ID 655a1b... titled "Setup ML Pipeline".
  2. Globex Corporation (a competitor or malicious tenant) observes, guesses, or intercepts task ID t1 via API logs or enumeration.
  3. Globex sends a PUT /api/tasks/655a1b... request authenticated with Globex's session headers.
  4. If the backend executes col.update_one({"_id": task_id}, {"$set": updates}), MongoDB finds document t1 and executes the update!
  5. Outcome: Globex successfully closes, alters, or destroys Acme's private business data. This violates tenant isolation (Broken Object Level Authorization / IDOR).
Prevention in Lab 15.1: By enforcing {"_id": task_id, "tenant_id": tenant_id}, MongoDB requires both conditions. Globex's request will find 0 matches, returning modified_count = 0 and blocking the attack.
Activity 2 Analysis: Migration Idempotency
Question: Predict whether the tenant's document count in the new database will double, stay the same, or something else on a repeat migration run?

Technical Prediction & Proof:

  • Prediction: The target document count will stay exactly the same (2 documents for tenant-acme).
  • Why it doesn't double: An ordinary insert_one() or insert_many() would generate duplicate documents with new _ids on every run.
  • Upsert on Natural Key: The migration executes:
    target_col.update_one(
      {"tenant_id": doc["tenant_id"], "title": doc["title"]},
      {"$set": doc},
      upsert=True
    )
  • On the repeat run, MongoDB matches existing documents by (tenant_id, title) and performs an in-place update rather than an insert.
Verification: Both source and target document counts remain 2, and SHA-256 content hashes match perfectly.
