1. Executive Architectural Overview & Core Concepts

In developmental MongoDB deployments (such as Chapter 8), clusters are commonly initialized without internal membership validation or administrative users. In production enterprise environments, this exposes the infrastructure to rogue node infiltration, data tampering, and unauthorized administrative compromise. Chapter 13 addresses three essential operational tiers:

Tier 1: Keyfile Auth (Docker)

3-member replica set with 756-byte cryptographic keyfile (chmod 400). Intra-cluster HMAC mutual trust and root admin bootstrapping via the Localhost Exception.

Tier 2: Kubernetes StatefulSet

Declarative cloud orchestration using a Headless Service (clusterIP: None) for stable CoreDNS addressing and volumeClaimTemplates for per-pod persistent storage.

Tier 3: Terraform & Cloud Atlas

Infrastructure-as-Code provisioning of an M0 free-tier cluster in AWS Mumbai (AP_SOUTH_1) with automated RBAC user and IP access list whitelisting.

2. Activity 1: Production Replica Set with Docker Compose
Keyfile Authentication vs Application RBAC

Keyfile Authentication enforces mutual trust between nodes, not client users. Every cluster member mounts the same random secret file (/etc/mongodb/keyfile). Nodes authenticate internal heartbeats and replication streams via HMAC-SHA, rejecting any rogue mongod.

Application RBAC manages human users and microservices connecting on standard ports, enforcing least privilege (e.g. readWriteAnyDatabase).

Order of Operations & Localhost Exception

Enabling --auth and --keyFile locks out all unauthenticated access. MongoDB solves this initial bootstrap dilemma via the Localhost Exception:

  1. Generate 756-byte keyfile: openssl rand -base64 756 > keyfile.
  2. Start containers with --replSet rs0 --auth --keyFile.
  3. Initiate cluster: rs.initiate(...) elects Primary.
  4. Bootstrap superuser (admin:AdminPass123!) on Primary before auth locks.
  5. All subsequent queries require authenticated credentials.

  _id: "rs0",

5. Production Connection String Parameter Breakdown
mongodb://admin:AdminPass123!@host.docker.internal:27017,host.docker.internal:27018,host.docker.internal:27019/admin?replicaSet=rs0&authSource=admin

• admin:AdminPass123!: Authenticated credentials provisioned during the initial bootstrapping phase.
• 3-Node Seedlist: Allows client drivers to discover the active Primary even if node 0 is offline during failover.

• replicaSet=rs0: Mandates topology discovery, tracking election state changes and routing writes exclusively to Primary.
• authSource=admin: Designates the authentication database where user credentials and privileges reside.

6. Activity 2: Kubernetes StatefulSet for MongoDB
Why Deployments Fail

Pods in a Deployment are stateless and interchangeable. Restarts generate random names (e.g. mongo-9b8f-1) and new IPs. Because member identities are baked into rs.conf(), pod restarts destroy cluster topology.

Headless Service (clusterIP: None)

Bypasses kube-proxy load-balancing. CoreDNS creates stable A-records for each pod: mongo-0.mongo.nosql-labs.svc.cluster.local. Pods maintain direct peer-to-peer addressing across restarts.

volumeClaimTemplates

Dynamically provisions a dedicated PersistentVolumeClaim per pod (mongo-data-mongo-0). If a pod is rescheduled onto a different worker node, it re-attaches to its exact storage volume without data collision.

7. Architectural Prediction & Verification

Question: Predict what serviceName field the StatefulSet needs to reference for stable pod-naming to work, and what would break if it referenced the wrong Service (or none at all)?

Technical Answer & Verification:
1. Required Reference: The StatefulSet spec must explicitly specify serviceName: mongo, matching the exact name of the headless Service created in 01-headless-service.yaml.
2. Consequence of Misconfiguration: The StatefulSet controller relies on serviceName to register predictable DNS A-records in CoreDNS. If missing or misconfigured, no per-pod DNS records are created. As a result, pods cannot discover each other; the initialization Job (03-replicaset-init-job.yaml) calling rs.initiate() fails with host resolution errors; and heartbeats fail, leaving the cluster permanently broken.

8. Terraform for MongoDB Atlas (main.tf)

Declarative cloud provisioning automates the deployment of fully managed MongoDB Atlas clusters using Infrastructure-as-Code (IaC). The main.tf configuration defines:

Provider & Cluster Specification
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    mongodbatlas = { source = "mongodb/mongodbatlas", version = "~> 1.16" }
  }
}
resource "mongodbatlas_cluster" "training" {
  name                   = "training-cluster"
  cluster_type           = "REPLICASET"
  provider_name          = "AWS"
  provider_region_name   = "AP_SOUTH_1" # Mumbai
  provider_instance_size_name = "M0"     # Free tier
  mongo_db_major_version = "7.0"
}
User Security & Network Whitelist
resource "mongodbatlas_database_user" "lab_user" {
  project_id         = mongodbatlas_project.nosql_labs.id
  username           = "lab_user"
  password           = var.atlas_user_password
  auth_database_name = "admin"
  roles { role_name = "readWriteAnyDatabase", database_name = "admin" }
}
resource "mongodbatlas_ip_access_list" "allow_all" {
  project_id = mongodbatlas_project.nosql_labs.id
  cidr_block = "0.0.0.0/0"
  comment    = "Training IP Access"
}
