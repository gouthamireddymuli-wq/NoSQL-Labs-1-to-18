Activity 2: Kubernetes StatefulSet for MongoDB

Declarative Cloud-Native Orchestration with Headless Services & Storage Isolation

StatefulSet (apps/v1)
Why Deployments Fail for MongoDB

A plain Kubernetes Deployment treats pods as completely interchangeable cattle. When a pod restarts, it receives a new, random hostname and IP. In a MongoDB replica set, member identities are permanently baked into rs.status(). Pod churn destroys the topology.

Headless Service & CoreDNS

Configuring clusterIP: None creates a Headless Service. Kubernetes bypasses proxy load-balancing and directly registers stable DNS A-records: mongo-0.mongo.nosql-labs.svc.cluster.local. Each pod is uniquely and directly addressable.

volumeClaimTemplates Isolation

Instead of a single shared volume, volumeClaimTemplates dynamically provisions an independent PersistentVolumeClaim per pod (mongo-data-mongo-0, mongo-data-mongo-1). When rescheduled to another physical worker node, the pod reconnects to its exact disk.

Lab Activity Question & Architectural Prediction
Prediction required before inspecting 02-statefulset.yaml:
Question:

"Predict what serviceName field the StatefulSet needs to reference for stable pod-naming to work, and what would break if it referenced the wrong Service (or none at all)?"

Verified Technical Answer:
  • Required Reference: The StatefulSet spec must specify serviceName: mongo, which matches the exact name of the headless Service declared in 01-headless-service.yaml.
  • What Breaks if Missing or Wrong: CoreDNS relies on spec.serviceName to register predictable DNS A-records (mongo-0.mongo.nosql-labs.svc.cluster.local) for each ordinal pod. If missing or misconfigured, no per-pod DNS records are created.
  • Consequence on MongoDB Cluster: Pods cannot discover each other by DNS name. The one-shot initialization Job (03-replicaset-init-job.yaml) calling rs.initiate() fails with host resolution errors. Inter-node heartbeats fail, preventing primary elections and rendering the replica set completely non-functional.
  • What if a standard (non-headless) service is used? Traffic sent to mongo would round-robin across pods instead of reaching the specific replica set member, causing corrupt quorum handshakes and replication failures.
